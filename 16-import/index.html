    Часть XVI. Механика импорта: от import x до исполняемого модуля#

    Уровень API уже разобран: sys.modules и __import__ (7.9), программный importlib (7.12), формат .pyc (15.2), импорт-режимы pytest (13.6). Здесь — сам конвейер: как стейтмент превращается в байт-код, где живёт кэш модулей, кто и в каком порядке собирает sys.path, как устроены finders, specs и loaders, чем namespace-пакет отличается от обычного, почему возникают круговые импорты, как работает ленивая загрузка и reload, какие бывают виды модулей, как писать свои импорт-хуки и как диагностировать медленный старт процесса. Разделы идут по ходу движения модуля: от стейтмента — через поиск и загрузку — к кухне диагностики. Все примеры проверены на CPython 3.12; версионные оговорки — по месту.

    16.1. Полный путь стейтмента: от IMPORT_NAME до sys.modules#

    import — обычная инструкция языка, и у неё есть байт-код. Компилятор переводит стейтмент в IMPORT_NAME, который вызывает встроенную __import__ (7.9):

    import dis

dis.dis(compile("import a.b.c", "<s>", "exec"))
#   1           2 LOAD_CONST               0 (0)      # level = 0
#               4 LOAD_CONST               1 (None)   # fromlist = None
#               6 IMPORT_NAME              0 (a.b.c)
#               8 STORE_NAME               1 (a)      # ← связывается только корень!
#
dis.dis(compile("from a.b import c", "<s>", "exec"))
#   1           2 LOAD_CONST               0 (0)
#               4 LOAD_CONST               1 (('c',)) # fromlist = ('c',)
#               6 IMPORT_NAME              0 (a.b)
#               8 IMPORT_FROM              1 (c)      # берём атрибут модуля
#              10 STORE_NAME               1 (c)

    Два следствия прямо из листинга. Первое: import a.b.c исполняет a, a.b, a.b.c — но связывает в пространстве имён только a; добраться до c без from a.b import c можно как a.b.c. Второе: from a.b import c — это тот же IMPORT_NAME для пакета плюс IMPORT_FROM, то есть чтение атрибута уже импортированного модуля. Никакой «экономии на импорте» у from нет — исполняется всё то же самое.

    Дальше IMPORT_NAME вызывает __import__('a.b.c', globals(), locals(), fromlist, level), а внутри — конвейер из четырёх шагов:

    1. кэш: если имя уже лежит в sys.modules — модуль возвращается немедленно, без диска и без исполнения;
    2. поиск: иначе имя передаётся цепочке finder'ов из sys.meta_path (16.3) — результат поиска это spec (16.4);
    3. загрузка: loader из spec создаёт объект модуля и исполняет его код;
    4. кэширование: готовый модуль кладётся в sys.modules и возвращается.

    Шаг 1 — не оптимизация, а часть семантики: тело модуля исполняется ровно один раз за процесс, сколько бы раз и из скольких мест его ни импортировали:

    # mod_once.py
print("MOD_ONCE: тело модуля исполнено")
VALUE = 42

    import sys
import mod_once
import mod_once            # второй import — тело НЕ исполняется
# MOD_ONCE: тело модуля исполнено        ← напечатано один раз

mod_once is sys.modules["mod_once"]      # True — это тот же объект

    Отсюда два классических эффекта. Положительный: модули с побочными эффектами (регистрация плагинов, патчинг, открытие ресурсов) срабатывают один раз, даже если десять подсистем сделали import. Отрицательный: тот же механизм означает, что повторный импорт не «обновит» модуль после изменения файла на диске — это работа для reload (16.8), и именно поэтому тесты с подменой окружения часто требуют перезагрузки конфиг-модулей (13.2).

    Что появляется у модуля при первом импорте#

    До исполнения тела интерпретатор создаёт объект модуля и заселяет его служебными атрибутами — полная анатомия свежесозданного модуля на 3.12:

    sorted(k for k in mod_once.__dict__ if k.startswith("__"))
# ['__builtins__', '__cached__', '__doc__', '__file__', '__loader__',
#  '__name__', '__package__', '__spec__']
    Атрибут Откуда берётся На что смотреть
    __name__ имя, по которому искали для __main__ — это имя запущенного скрипта, не модуля (15.2)
    __spec__ результат поиска (16.4) начиная с 3.4 (PEP 451) — «паспорт» модуля; None у __main__ в некоторых сценариях
    __loader__ из spec кто загрузил; удобно в логах и плагинах
    __file__ из spec.origin путь к исходнику; у builtin-модулей отсутствует (16.9)
    __cached__ из spec.cached путь к .pyc; None, если кэша нет
    __package__ spec.parent 'json' у json.decoder; 'json' у самого пакета
    __builtins__ словарь/модуль builtins технический канал, через который живут len, print и др. (7.10)
    __path__ только у пакетов список каталогов для поиска подмодулей; у обычного модуля этого атрибута нет — это и есть формальный критерий «пакетности»

    У regular-пакета json.__path__ — обычный list; у namespace-пакета — специальный _NamespacePath (16.5). __spec__.parent и __package__ всегда совпадают.

    sys.modules — обычный dict, и это фича#

    sys.modules — не магическая структура, а словарь «имя → модуль», и с ним можно делать всё, что делают со словарями. Две канонические техники. Первая — «тихий импорт» и проверка «уже импортировано?» (7.9): if 'json' in sys.modules стоит наносекунды и не тянет за собой загрузку. Вторая — заглушки: положить в sys.modules подменыш до импорта зависимого кода — стандартный приём тестов (13.3 подменяет модули через patch.dict(os.environ) и sys.modules-манипуляции), и того же механика работает у фреймворков для опциональных зависимостей:

    import sys, types
sys.modules["pysqlite2"] = types.SimpleNamespace(connect=lambda *a, **kw: None)
# теперь любой код, делающий `import pysqlite2`, получит заглушку

    ⚠️ Обратная сторона той же свободы: запись в sys.modules — глобальный эффект на весь процесс, читаемый любым кодом. Удалить оттуда системный модуль (del sys.modules['json']) — значит гарантировать себе повторное исполнение его тела при следующем импорте; иногда это нужно (перезагрузка в тестах), чаще — источник трудноуловимых двойных регистраций.

    16.2. sys.path: кто, что и в каком порядке кладёт#

    Поиск по диску ведёт PathFinder (16.3), но ходит он по sys.path — простому списку строк, который собирается из четырёх источников в момент старта. Порядок — это и есть приоритет поиска: побеждает первое совпадение.

    # Источник Что кладёт Как управлять
    1 «текущее место» каталог скрипта — при python script.py; '' (текущий каталог) — при -c и REPL; cwd — при -m флаг -P / PYTHONSAFEPATH (3.11+) убирает этот элемент
    2 PYTHONPATH все перечисленные каталоги, по порядку env (10.3); работает и в venv
    3 стандартная библиотека каталог stdlib интерпретатора + zip-архивы stdlib, если есть определяется при сборке; sys.prefix (11.32)
    4 site.py site-packages самого интерпретатора, user site-packages, всё из .pth-файлов PYTHONNOUSERSITE, -s, -I (11.32)

    Первый источник — самый коварный, потому что зависит от способа запуска. Один и тот же вопрос «что стоит в sys.path[0]?» даёт три разных ответа:

    $ python -c 'import sys; print(repr(sys.path[0]))'
''                                   # текущий каталог (пустая строка!)
$ python sdir/s.py                   # внутри s.py: print(repr(sys.path[0]))
'/…/sdir'                            # каталог скрипта, не cwd!
$ python -m pshow                    # внутри pshow.py: print(repr(sys.path[0]))
'/…/cwd'                             # cwd, откуда запустили -m

    Каталог скрипта вместо cwd — источник вечного сюрприза «почему мой модуль лежит рядом со скриптом и не импортируется, хотя я запускаю из корня проекта». При python sdir/s.py ищут в sdir/, а не в каталоге, откуда запустили. -m в этом смысле честнее: он кладёт в sys.path[0] текущий каталог — потому и говорят, что «для своего пакета запускайте -m, а не путь к файлу».

    Подмена stdlib из текущего каталога и защита -P#

    Тот факт, что «текущее место» стоит первым, означает: файл random.py в текущем каталоге перекроет stdlib-ный random. Это фича (быстрые локальные оверрайды), но и вектор: скачанный архив с setup.py, запущенный в каталоге с вредоносным random.py, исполнит его вместо модуля stdlib. С 3.11 есть выключатель:

    $ cat random.py
print("SHADOW: это мой random.py из текущего каталога")
x = 42
$ python -c 'import random; print(hasattr(random, "x"))'
SHADOW: это мой random.py из текущего каталога
True                                  # ← перекрыли stdlib
$ python -P -c 'import random; print(hasattr(random, "x"))'
False                                 # -P: sys.path[0] не добавлен
$ PYTHONSAFEPATH=1 python -c 'import random; print(hasattr(random, "x"))'
False                                 # то же через окружение (10.3)

    -I (isolated) включает -P в комплекте с -s и -E — игнорировать user site и PYTHON*-переменные; в 13.11 он фигурирует как режим для воспроизводимых прогонов.

    .pth-файлы: самый недооценённый механизм site.py#

    site.py сканирует site-packages на файлы *.pth. Каждая строка файла — либо путь, который добавляется в sys.path, либо строка, начинающаяся с import — исполняемый код, который запускается при каждом старте интерпретатора. Второе и есть механика нескольких «волшебств»: editable-установки pip кладут __editable__*.pth, а хуки инструментария — sitecustomize/usercustomize (16.10). В -X importtime-трассе старта видно, сколько стоит этот слой: в нашем прогоне весь site — около 1.4 мс из ~6.3 мс общего импорта json вместе со стартом (16.11).

    Проверить, кто именно собрал текущий sys.path, можно на месте: пути до «текущего места» и PYTHONPATH уже стоят к моменту, когда исполняется ваш код, а всё после stdlib — работа site. Сравните python -c 'import sys; print(len(sys.path))' и python -S -c ... — разница покажет вклад site.py.

    16.3. Finders и path hooks: как интерпретатор ищет модуль#

    Если имени нет в sys.modules, оно уходит цепочке meta path finders — объектов с методом find_spec(name, path, target=None), лежащих в sys.meta_path. Первый, кто вернёт spec (16.4), выигрывает; никто — ModuleNotFoundError. Список по умолчанию на 3.12 короткий:

    import sys

def name(x):
    return getattr(x, "__name__", None) or type(x).__name__

print(*[name(f) for f in sys.meta_path], sep="\n")
# BuiltinImporter      ← модули, скомпилированные в бинарник (sys, builtins, _imp…)
# FrozenImporter       ← модули, замороженные в бинарник на этапе сборки (16.9)
# PathFinder           ← всё, что ищется по sys.path на диске и в zip

    Первые два — «бесплатные» (поиск — это проверка факта в таблице интерпретатора, диска нет), поэтому они и стоят перед PathFinder. Практическое следствие: модуль с именем sys из текущего каталога не перекроется вашим файлом sys.py — BuiltinImporter ответит раньше. Перекрыть builtin нельзя, а вот обычный модуль stdlib — можно (16.2).

    Вся нагрузка на PathFinder. Его алгоритм для каждого элемента sys.path:

    1. спросить у sys.path_importer_cache — есть ли уже finder для этого каталога;
    2. если нет — пройтись по sys.path_hooks, фабрикам finder'ов: хук вызывается с путём и либо возвращает path entry finder, либо бросает ImportError («это не мой формат»);
    3. найденный finder спросить про find_spec(name).

    Устройство хуков видно напрямую:

    def name(x):
    return getattr(x, "__name__", None) or type(x).__name__

print(*[name(h) for h in sys.path_hooks], sep="\n")
# zipimporter              ← элементы пути «.zip» обслуживает zipimport (16.9)
# path_hook_for_FileFinder ← обычные каталоги

print(len(sys.path_importer_cache))   # 7 — по записи на уже встречавшийся путь

    Заметьте порядок: zip-хук стоит раньше файлового, поэтому каталог и архив с одинаковым именем разрешаются в пользу архива. path_importer_cache — кэш «путь → finder»: листинг каталога сканируется один раз, а не на каждый импорт; именно поэтому свежесозданные файлы в путях иногда «не видны» до importlib.invalidate_caches() (16.8).

    Суффиксы: расширение > исходник > байт-код#

    FileFinder создаётся с тремя наборами суффиксов — и перебирает их в фиксированном порядке приоритета:

    Приоритет Суффиксы (3.12, Linux) Loader
    1 .cpython-312-x86_64-linux-gnu.so, .abi3.so, .so ExtensionFileLoader — бинарные C-расширения (16.9)
    2 .py SourceFileLoader — исходники
    3 .pyc SourcelessFileLoader — байт-код без исходника

    Список живёт в importlib.machinery.EXTENSION_SUFFIXES / SOURCE_SUFFIXES / BYTECODE_SUFFIXES. Приоритет означает: если рядом лежат m.py и m.pyc, импортируется .py (а .pyc используется как кэш, 15.2); «голый» .pyc без исходника тоже импортируется — SourcelessFileLoader именно это и делает, и это законный способ поставлять код без исходников.

    Узнать, «как бы импортировался модуль», не исполняя его, можно публичным API:

    import importlib.util

spec = importlib.util.find_spec("json")
print(spec.name, "|", spec.origin, "|", type(spec.loader).__name__)
# json | /…/python3.12/json/__init__.py | SourceFileLoader

    ⚠️ find_spec не исполняет сам модуль, но исполняет родительские пакеты: find_spec("json.decoder") сначала импортирует json целиком, включая тело __init__.py. Для тяжёлых пакетов «просто проверить наличие» через find_spec — не бесплатная операция. Для проверки «есть ли такой модуль вообще» без побочных эффектов у топ-уровня есть дешёвый трюк: name in sys.stdlib_module_names (3.10+) — статическое множество имён stdlib — плюс ваши собственные знания о зависимостях; а дальше find_spec, если риск побочек оправдан.

    16.4. ModuleSpec и Loader: контракт импорта#

    Finder возвращает не модуль, а spec — «чертёж»: где модуль лежит и кто его загрузит. Всё, что решает импорт-система, решается на основании spec:

    Поле spec Что содержит Куда попадает у модуля
    name полное имя (json.decoder) __name__
    loader объект-загрузчик __loader__
    origin «место»: путь, 'built-in', 'frozen', None __file__ (если has_location)
    cached путь к pyc-кэшу __cached__
    parent имя пакета-родителя __package__
    submodule_search_locations пути для подмодулей __path__ (пакеты)

    Loader — исполнитель чертежа. Контракт из двух методов (PEP 451):

    • create_module(spec) — создать объект модуля (по умолчанию None — «создай стандартный ModuleType»; возвращать свой объект — продвинутый случай, так делают C-расширения и LazyLoader, 16.7);
    • exec_module(module) — исполнить код модуля в его пространстве имён.

    Внутри SourceFileLoader.exec_module живёт вся pyc-кухня из 15.2: get_code() проверяет __pycache__, валидирует magic number и mtime, при промахе компилирует и пишет кэш. Разница между «импортом» и «ручной загрузкой» в том, кто вызывает эти методы: обычно — bootstrap-механизм, но ничто не мешает вам сделать то же самое руками. Классический сценарий — модуль с нестандартным расширением (файл plugin.txt с питоновским кодом):

    import sys
from importlib.util import spec_from_file_location, module_from_spec
from importlib.machinery import SourceFileLoader

# наивная попытка: расширение не входит в наборы суффиксов loader'ов (16.3)
spec = spec_from_file_location("plugin", "/…/plugin.txt")
print(spec)
# None  ← не исключение, просто None: «не знаю, чем такое грузить»

# правильная попытка: loader передаётся явно
spec = spec_from_file_location(
    "plugin", "/…/plugin.txt",
    loader=SourceFileLoader("plugin", "/…/plugin.txt"))
mod = module_from_spec(spec)
sys.modules["plugin"] = mod          # ← регистрация ДО исполнения
spec.loader.exec_module(mod)
print(mod.RESULT)                    # 42

    Три детали, без которых ручная загрузка ломается. Первая: module_from_spec только создаёт пустой модуль с заполненными __spec__/__loader__/__name__ — исполнение делает exec_module, забытый чаще всего. Вторая: регистрация в sys.modules до exec_module — не перестраховка: тело модуля может ссылаться на самого себя (plugin.some_func после import plugin внутри собственного кода, pickle, dataclasses с self-references) — оно увидит себя в кэше только если его туда положили заранее. Третья: spec_from_file_location для неизвестного суффикса молча возвращает None — проверяйте результат, прежде чем писать spec.loader.

    Ручная загрузка — базовый строительный блок плагинных систем: «пройтись по каталогу, каждый *.py загрузить с уникальным именем, собрать классы-плагины» — это ровно четыре строки поверх кода выше. Но если плагины лежат в обычных пакетах на sys.path, нагрузите систему штатно: finder'ами (16.10), а не ручным перебором.

    16.5. Namespace-пакеты (PEP 420): пакет без __init__.py#

    Каталог с __init__.py — regular package: исполняется __init__.py, __path__ — один каталог. Каталог без __init__.py, обнаруженный при поиске, — не ошибка: PathFinder запоминает его как portion («долю» пакета) и продолжает идти по sys.path. Если к концу пути нашлись только portions — собирается namespace package: модуль без исполняемого кода, чей __path__ — объединение всех долей.

    Эксперимент, в котором видна вся механика. Два корня, в каждом свой каталог pkg без __init__.py:

    r1/pkg/sub1.py          # print("sub1 из r1")
r2/pkg/sub2.py          # print("sub2 из r2")

    import pkg, pkg.sub1, pkg.sub2          # PYTHONPATH=r1:r2
# sub1 из r1
# sub2 из r2

type(pkg.__path__).__name__             # '_NamespacePath' — не list!
list(pkg.__path__)                      # ['…/r1/pkg', '…/r2/pkg'] — обе доли
pkg.__spec__.origin                     # None — исполняемого кода не было

    Оба подмодуля импортировались, хотя ни один каталог pkg не содержит __init__.py: поиск подмодулей идёт по обоим элементам __path__. В отличие от regular-пакета, у namespace-пакета нет ни исполняемого __init__, ни __file__ (поэтому «путь к пакету» через pkg.__file__ — источник AttributeError).

    Теперь ловушка, на которой спотыкаются даже опытные проекты. Добавим третий корень с регулярным пакетом — с __init__.py:

    r3/pkg/__init__.py      # print("REGULAR: __init__ из r3")
r3/pkg/sub3.py

    import pkg                              # PYTHONPATH=r1:r2:r3
# REGULAR: __init__ из r3               ← __init__ исполнился

import pkg.sub1
# ModuleNotFoundError: No module named 'pkg.sub1'

list(pkg.__path__)                      # ['…/r3/pkg'] — одна доля вместо трёх

    Регулярный пакет, найденный в любом месте пути, немедленно останавливает поиск и затирает собранные к этому моменту namespace-доли. Порядок в sys.path решает всё: portions из r1 и r2 не «дополняют» regular-пакет из r3, а выбрасываются. Это самая частая практическая ошибка с namespace-пакетами: «мы добавили наш каталог в PYTHONPATH, почему-то половина модулей пропала» — значит, где-то раньше по пути нашёлся одноимённый каталог с __init__.py.

    Regular package Namespace package
    __init__.py обязателен, исполняется отсутствует
    __path__ list из одного каталога _NamespacePath из всех долей
    __file__ путь к __init__.py отсутствует
    __spec__.origin путь к __init__.py None
    Подмодули только из своего каталога из всех долей по всему пути
    Перекрытие побеждает namespace всегда проигрывает regular при любом порядке

    Зачем это нужно в реальности: namespace-пакет — способ нескольким независимым дистрибутивам поставлять код под общим корнем. Классические примеры — google.* (пакеты protobuf, google-auth и десятки других кладут свои google/-каталоги без __init__.py, и все они сливаются в один namespace) и zope.* из эпохи Zope. Механика существует с 3.3 (PEP 420), и с тех пор это не экзотика, а штатный способ: если вы делаете монорепо с несколькими устанавливаемыми пакетами под общим именем — namespace-пакет избавляет от конфликтов __init__.py при установке (подробнее о том, как это выглядит в пакетах — перспективно в Части XIV про упаковку).

    16.6. Круговые импорты: анатомия и лечение#

    Круговой импорт — это когда a импортирует b, а b — a. У фреймворков с ленивой загрузкой моделей такая связка возникает сама (модель ссылается на пользователя, пользователь — на модель). Чтобы понять, почему одни круги падают, а другие нет, достаточно одной фразы: модуль попадает в sys.modules до начала исполнения своего тела (16.1, шаг 4 — точнее, регистрация происходит на входе в загрузку). С одной стороны, именно это гарантирует одноразовость и останавливает бесконечную рекурсию: встретив круг, система видит модуль в кэше и возвращает «как есть». С другой — «как есть» на этот момент означает полуисполненный модуль: в нём есть только то, что успело исполниться до точки круга.

    Разберём оба варианта. Падающий круг — from-импорт на верхнем уровне:

    # ca.py
import cb
X = "значение X из a"

# cb.py
from ca import X      # ca ещё исполняется: X не существует
Y = 1

    $ python -c "import ca"
ImportError: cannot import name 'X' from partially initialized module 'ca'
(most likely due to a circular import) (/…/ca.py)

    Сообщение прямо называет механику: «partially initialized module». Порядок событий: import ca → тело ca началось, в sys.modules уже лежит ca (полупустой) → import cb → тело cb → from ca import X → X читается как атрибут полуисполненного модуля (16.1: IMPORT_FROM) → атрибута нет, потому что строка X = ... ещё не исполнялась.

    Работающий вариант — тот же круг, но import вместо from и обращение к атрибуту после завершения круга:

    # cb.py
import ca
def get_x():
    return ca.X        # исполнится позже, когда ca будет дописан

print("ca" in sys.modules)   # True — уже на момент исполнения тела cb

    import ca, cb
cb.get_x()            # 'значение X из a' — работает

    Здесь import ca внутри cb не читает атрибутов — он просто получает полупустой объект из кэша; а get_x дотягивается до ca.X в момент вызова, когда оба модуля давно дописаны. Отсюда общее правило: from x import y требует готовности y в момент импорта, import x — только в момент использования.

    Каждый симптом — к своему лекарству:

    Симптом Причина Лечение
    ImportError: cannot import name … (partially initialized) from-импорт атрибута, которого ещё нет заменить на import + доступ через модуль; либо перенести импорт ниже определяемого имени
    Круг «конфиг ↔ всё остальное» общие константы затянуты в большой модуль вынести общее в третий листовый модуль без зависимостей
    Круг только для аннотаций типов аннотации исполняются в момент определения if TYPE_CHECKING: (5.15) — аннотации не исполняются в рантайме
    Круг «модуль ↔ его плагины» плагины регистрируются в базовом модуле регистрация через хук: базовый модуль объявляет __getattr__ (PEP 562, 16.7) и не импортирует плагины сам
    Круг из-за side-эффектов в __init__.py __init__ тянет тяжёлые подмодули урезать __init__.py до лёгких реэкспортов; тяжёлое — лениво

    Круговые импорты в чистом виде — не баг языка, а симптом архитектуры: модуль, который «и константы, и типы, и регистрация», почти всегда просится на разбиение. Но знать механику нужно, чтобы отличать честный круг (чинится перестановкой импорта) от цикла в графе зависимостей (чинится только архитектурой).

    16.7. Ленивый импорт: PEP 562 и LazyLoader#

    Идея ленивого импорта: модуль или атрибут не загружается в момент import, а откладывается до первого обращения. В stdlib для этого есть два механизма разного масштаба.

    __getattr__ на уровне модуля (PEP 562, 3.7+)#

    У модуля, как у класса, можно определить __getattr__ — его вызывают, когда обычный поиск атрибута не сработал:

    # lazy_mod.py
_heavy = None

def __getattr__(name):
    if name == "heavy":
        global _heavy
        if _heavy is None:
            print("LAZY: тяжёлый ресурс загружен при первом обращении")
            _heavy = "тяжёлый"
        return _heavy
    raise AttributeError(f"module {__name__!r} has no attribute {name!r}")

def __dir__():
    return sorted(set(globals()) | {"heavy"})    # чтобы dir() не врал

    import lazy_mod
# (тишина — ничего не загружено)
dir(lazy_mod)         # [..., 'heavy'] — атрибут анонсирован
lazy_mod.heavy        # LAZY: тяжёлый ресурс загружен при первом обращении
lazy_mod.heavy        # второй раз — уже тихо: значение закэшировано в globals

    Это самый гибкий инструмент: так делают реэкспорты с отложенной загрузкой («from mypkg import BigThing должно работать, но BigThing грузится только когда нужен»), устаревшие шимы («атрибут ещё отдаётся, но warning»), и типовое разрешение круговых импортов из 16.6. Класс-паттерн библиотеки lazy_loader: модуль-обёртка объявляет в __getattr__ список «настоящих» подмодулей и грузит их по требованию.

    importlib.util.LazyLoader: отложенный весь модуль#

    Более радикальный механизм: модуль создаётся, но его класс подменяется на _LazyModule, и тело не исполняется до первого обращения к любому атрибуту:

    import sys
from importlib.util import spec_from_file_location, module_from_spec, LazyLoader

spec = spec_from_file_location("lz", "/…/plain_mod.py")
spec.loader = LazyLoader(spec.loader)     # оборачиваем настоящий loader
mod = module_from_spec(spec)
sys.modules["lz"] = mod
spec.loader.exec_module(mod)
# (тишина — тело НЕ исполнено)

type(mod).__name__     # '_LazyModule' — класс-приманка
_ = mod.VAL            # первый доступ к атрибуту…
type(mod).__name__     # 'module' — класс вернули обычному, тело исполнено

    LazyLoader — это тот самый «продвинутый случай» create_module из 16.4: loader создаёт модуль с классом _LazyModule, чей __getattribute__ при первом обращении исполняет тело через настоящий loader и восстанавливает обычный класс. Лень прозрачна: после первого касания модуль неотличим от нормально импортированного.

    ❌ Ловушка обоих механизмов: from mod import name пробуждает ленивую загрузку. IMPORT_FROM читает атрибут модуля (16.1) — это уже «первое обращение». Лень работает только пока с модулем обращаются как с модулем (mod.name), и не работает, когда имя достают сразу.

    Цена вопроса — секунды старта CLI-приложений и тысячи минут CI. Прагматика: ленивыми делают то, что нужно не каждому запуску — тяжёлые бэкенды опциональных зависимостей, подкоманды CLI, драйверы. Полную автоматизацию предлагал PEP 690 (ленивый импорт по умолчанию) — PEP отклонён: неявная лень ломает модули с осмысленными сайд-эффектами и monkeypatch-паттерны; лень в Python остаётся явной обязанностью автора API. Замер реальной экономии — в 16.11 и бенчмарках (B2, B5): четыре «просто импортируем сверху» модуля стоят ~15 мс на каждый запуск процесса.

    16.8. reload: механика перезагрузки и её границы#

    importlib.reload(module) — попытка «перечитать» модуль без перезапуска процесса. Механика: берётся существующий module.__spec__, loader заново читает код (исходник с диска — pyc-инвалидация работает как обычно, 15.2) и исполняет его в том же самом объекте модуля. Namespace не пересоздаётся, а переиспользуется: reload не «очищает» модуль, а дописывает поверх.

    # cfg.py: VAL = 1
import sys, os, importlib
import cfg
from cfg import VAL                 # отложенная ссылка на значение

# …файл cfg.py переписан: VAL = 2 …
importlib.invalidate_caches()
importlib.reload(cfg)

cfg.VAL                             # 2    ← модуль видит новое
VAL                                 # 1    ← from-import сделан ДО reload: устарел
cfg is sys.modules["cfg"]           # True — identity сохранена

    Из вывода видны оба ключевых факта: объект модуля тот же (все, кто держал ссылку, автоматически «на новом»), но ссылки, вытащенные через from до reload, остаются старыми — они указывали на конкретное значение, а VAL = 2 лишь записало новое значение в атрибут модуля (7.2: переприсваивание не обновляет чужие ссылки). То же с классами: экземпляры, созданные старым классом, остаются экземплярами старого класса — isinstance после reload начнёт подводить.

    Что reload обновляет и что нет:

    После reload
    Атрибуты модуля, заданные в коде ✅ перезаписаны новыми
    Атрибуты, удалённые из новой версии ❌ остаются — namespace не очищается; забытые «мусорные» имена живут
    from mod import x чужих модулей ❌ старые значения
    Экземпляры старых классов ❌ старый класс в __class__
    Кэши (functools.cache на функции модуля) ⚠️ функция пересоздана — кэш пуст, но это сюрприз для полупрогретых процессов
    Реестры через __init_subclass__ (6.8) ⚠️ классы зарегистрируются повторно — в реестре появятся дубли

    Двойная регистрация — самый болезненный пункт: reload декорированного/регистрирующегося кода исполняет декораторы и __init_subclass__ заново. Если реестр — обычный список, вы получите два элемента; если dict по имени — новое затрёт старое, и это часто желаемое поведение. Именно поэтому «горячая перезагрузка» плагинов через reload требует либо реестров-словарей, либо явного hook'а «before/after reload».

    Когда это вообще нужно. Рабочая тройка: интерактивная разработка (REPL/Jupyter — «поменял модуль, не хочу перезапускать ядро с GPU-контекстом»), плагинные системы с перезагрузкой, тесты, которые правят конфиг-модули и перезагружают их (13.2). В проде reload — анти-паттерн: семантика «дописывания поверх» гарантирует, что долго живущий процесс после сотен reload'ов несёт в себе слоёный пирог старых объектов.

    И последняя деталь конвейера: importlib.invalidate_caches(). FileFinder (16.3) кэширует листинг каталога и проверяет его по mtime каталога; на локальной ФС с наносекундным mtime новые файлы видны почти сразу, но на сетевых ФС, в контейнерах с огрубленным mtime и в тестах, которые создают файлы с подделанными временами, свежий модуль не находится — лечится ровно этим вызовом. Он же нужен после того, как вы вручную испортили sys.path_importer_cache.

    16.9. Особые виды модулей: builtin, frozen, extension, zipimport#

    Не всё, что импортируется, живёт в .py-файлах. Полная карта:

    Вид Loader __spec__.origin __file__ Примеры
    builtin BuiltinImporter 'built-in' ❌ нет sys, builtins, _imp, _io
    frozen FrozenImporter 'frozen' ❌ нет zipimport, _frozen_importlib
    extension ExtensionFileLoader путь к .so/.pyd ✅ zlib, _json, numpy._core
    source SourceFileLoader путь к .py ✅ почти всё
    sourceless SourcelessFileLoader путь к .pyc ✅ поставка без исходников
    namespace NamespaceLoader None ❌ нет google.* (16.5)

    Builtin — модули, скомпилированные в бинарник интерпретатора (sys.builtin_module_names; в начале списка — служебные _abc, _ast, _asyncio, _bisect…). Их нельзя перекрыть файлом (16.3: BuiltinImporter стоит первым) и у них нет файла — потому inspect.getsource(sys) падает, а sys.__file__ — AttributeError. Достоинство builtin — нулевая стоимость импорта: нет поиска на диске вообще.

    Frozen — модули, чей байт-код вшит в бинарник при сборке. История с курицей и яйцом: сам импорт-механизм (_frozen_importlib, _frozen_importlib_external) должен существовать до того, как заработает импорт, — поэтому он заморожен в бинарник и разгоняет всё остальное. С 3.11 фризится и «стартовый критичный» набор stdlib (zipimport и др.), управляется флагом -X frozen_modules=on|off (по умолчанию on в release-сборках; off — в debug-сборках, чтобы править stdlib без пересборки):

    import sys, zipimport
zipimport.__spec__.origin          # 'frozen'
sys._xoptions                      # {'frozen_modules': 'off'} — при -X frozen_modules=off

    Флаг влияет на frozen-модули stdlib; заморозить свой код (получить самодостаточный бинарник) — задача внешних инструментов (PyInstaller и компания), но механика та же: байт-код кладётся в таблицу FrozenImporter.

    Extension — C-расширения: ExtensionFileLoader загружает динамическую библиотеку и ищет в ней точку входа PyInit_<имя модуля>; дальше весь импорт сводится к одному вызову в C. Суффиксы (.cpython-312-x86_64-linux-gnu.so, .abi3.so) кодируют ABI — отсюда привязка колёс к версии интерпретатора (17.1). Подробный разбор C-стороны — тема отдельной части (XVIII); здесь важно, что для импорт-механики extension ничем не отличается от source: тот же PathFinder, тот же FileFinder, просто другой суффикс с высшим приоритетом (16.3).

    zipimport — импорт прямо из zip-архива, без распаковки. Работает через path hook (16.3): элемент sys.path, указывающий на .zip, обслуживает zipimporter, который читает каталог архива и грузит модули оттуда:

    import sys, zmod                  # bundle.zip добавлен в sys.path
zmod.__file__                     # '…/bundle.zip/zmod.py'  ← путь внутрь архива
type(zmod.__loader__).__name__    # 'zipimporter'
zmod.ZIPVAL                       # 7 — обычный модуль во всём, кроме файловой системы

    Пакеты в zip работают как обычно (архив — «каталог» для PathFinder). Тонкость — .pyc: если в zip лежит исходник, zipimport компилирует его при каждом импорте (писать __pycache__ внутрь архива некуда); положите в архив заранее скомпилированный m.pyc — и zip-импорт сравнивается по скорости с обычным каталогом (бенчмарк B4: 58 мкс против 396 мкс на исходнике). Практические применения: однофайловая дистрибуция приложений, embeddable-дистрибутивы, инструменты вроде PyInstaller (штатно таскают приложение в zipapp), и stdlib-зипы при сборке интерпретатора.

    Различать виды изнутри процесса удобно по sys.stdlib_module_names (3.10+) — статическому множеству имён stdlib — в паре с spec.origin: это и есть «проверка, что foo — не чья-то локальная подделка» (10.4).

    16.10. Кастомные импорт-хуки: от логгера до блокировщика#

    sys.meta_path — обычный список (16.3), и каждый, кто в него добавится, получит голос в решении «где взять модуль». Два канонических применения — наблюдение и запрет.

    Логгер импортов. Finder, который всё записывает и возвращает None (то есть не мешает остальным):

    import sys

log = []

class ImportLogger:
    def find_spec(self, name, path=None, target=None):
        log.append(name)
        return None                     # «не знаю такого» — ищите дальше

sys.meta_path.insert(0, ImportLogger()) # первым — видеть все запросы
import json

print(len(log))                         # 23 — столько имён затронул один import json
print(log[:6])
# ['json', 'json.decoder', 're', 'enum', 'types', 'operator']

    Двадцать три имени на «безобидный» import json — наглядная цена транзитивных зависимостей: тело json/__init__.py тянет json.decoder, тот — re, а re тянет enum, functools, operator и дальше по графу. Тот же приём в развитии (тайминг + вложенность) и есть -X importtime (16.11).

    Блокировщик. Finder, который бросает исключение на запрещённых именах:

    import sys

class ImportBlocker:
    BLOCKED = {"socket"}
    def find_spec(self, name, path=None, target=None):
        if name.split(".")[0] in self.BLOCKED:
            raise ImportError(f"[policy] импорт {name!r} запрещён политикой проекта")
        return None

sys.meta_path.insert(0, ImportBlocker())
try:
    import socket
except ImportError as e:
    print(e)      # [policy] импорт 'socket' запрещён политикой проекта

    Так работают «импорт-политики»: тестовые гарды («никто не должен тянуть сеть в юнит-тестах»), песочницы, license-контроль. ⚠️ Исключение из find_spec не глушится — оно убивает импорт целиком, поэтому блокировщик и работает; но это же значит: хук с багом роняет импорт чего угодно. Держите хуки маленькими и без зависимостей. Родственный механизм с более формальным контрактом — audit hooks: событие import поднимается на уровне C API для каждого импорта (10.7), и его нельзя перехитрить сменой sys.meta_path.

    Почему логгер «видит» 23 имени, а не 23+1: хук добавлен после старта, и всё уже импортированное интерпретатором (sys, os, сам sys.meta_path…) уже лежит в sys.modules — для них find_spec не вызывается вовсе. Хук, вставленный до всего (из sitecustomize), увидит и стартовый слой.

    sitecustomize и usercustomize. Это import-строки .pth-механики из 16.2, доведённые до стандарта: модуль sitecustomize (обычно кладут в site-packages) и usercustomize (в user site) импортируются site.py при каждом старте — если найдены. Здесь включают faulthandler глобально (10.8), ставят audit hooks, добавляют корпоративные пути. Порядок: sitecustomize раньше usercustomize; отключить слой целиком можно -S/-E. Именно поэтому в importtime-трассе они висят под site (16.11) — и почему «у меня на машине работает» иногда означает «у меня в sitecustomize лежит магия».

    Реальная жизнь хуков, с которыми вы уже встречались в книге: pytest переписывает assert ваших тестов через импорт-хук (assertion rewriting, 13.6) — перехватывая загрузку тестового модуля и подсовывая переписанный байт-код; coverage.py использует sys.settrace/sys.monitoring (с 3.12, 13.9) и C-расширение трассировки, но не import-хуки; виртуальные окружения работают через sys.path, собранный site.py (11.32). Импорт-система — самая легальная точка расширения Python: всё, что делают pytest и coverage, доступно и вам без единого форка интерпретатора.

    16.11. Диагностика старта: -X importtime#

    Флаг -X importtime (3.7+) печатает в stderr дерево всех импортов с таймингами:

    $ python -X importtime -c 'import json'          # PYTHONNOUSERSITE=1
import time: self [us] | cumulative | imported package
…
import time:       197 |       1420 | site
import time:      1110 |       3367 |       enum
import time:       385 |       4819 |     re
import time:       462 |       5696 |   json.decoder
import time:       338 |        338 |   json.encoder
import time:       224 |       6256 | json

    Читается так: отступ — глубина вложенности (кто кого импортировал: json → json.decoder → re → enum); self — собственное время модуля (исполнение тела без детей); cumulative — модуль вместе со всеми его зависимостями. На фрагменте выше видно всё: сам json/__init__.py стоит 224 мкс, но весь импорт — 6256 мкс, и почти всё время сидит в детях: re (4819 мкс) с его enum (3367 мкс) — классическая тройка «импортировал json — заплатил за re». Порядок строк — порядок завершения загрузки, снизу вверх по дереву.

    Глобальная картина старта процесса: site (1420 мкс) исполняется до вашего кода, и его стоимость платится даже за python -c 'pass'. Эквивалент через окружение — PYTHONPROFILEIMPORTTIME=1 (10.3) — удобно, когда флаг не пробросить (запуск через обёртку, tox, IDE).

    Методика работы с медленным стартом:

    1. Снять трассу реального запуска (python -X importtime your_app.py 2> imports.log) — не угадывать, а посмотреть топ по cumulative.
    2. Найти «слишком ранние» импорты: модули, которые импортируются при старте, но нужны одной команде/подкоманде → перенести в функцию или сделать ленивыми (16.7).
    3. Проверить тяжеловесов по self: большой self у __init__.py — исполняемый код на верхнем уровне пакета; кандидаты на разбиение.
    4. Зафиксировать бюджет в CI: сравнение importtime между коммитами ловит регрессии старта до пользователей.

    Бенчмарки к Части XVI#

    # B1. Тёплый кэш sys.modules против переисполнения модуля (CPython 3.12):
timeit("import json", number=20_000)               # ≈  137 нс за импорт (кэш)
timeit("from json import loads", number=20_000)    # ≈  340 нс (кэш + атрибут)
# 100 полных переисполнений json (вычищен из sys.modules):
# ≈ 493 мкс за импорт — в тысячи раз дороже тёплого кэша

    Повторный import — это dict-lookup (16.1); реальная цена импорта — только первый раз, и почти вся она — исполнение тела и его зависимостей.

    B2. Старт процесса (среднее по 20 запускам):

    Команда Время
    python -c 'pass' ≈ 9.3 мс
    python -S -c 'pass' (без site) ≈ 7.7 мс
    python -c 'import json' ≈ 16.7 мс
    python -c 'import json, urllib.request, argparse, xml.etree.ElementTree' ≈ 59.3 мс

    База старта — 9 мс, из них ~1.6 мс — site.py; «просто импортируем четыре модуля сверху» — плюс 50 мс к каждому запуску. Для CLI, который зовут в цикле (или в CI на тысячи джобов), это готовый аргумент за ленивую загрузку.

    B3. find_spec и кэш путей: 

    # 500 вызовов importlib.util.find_spec('json') по горячему кэшу: ≈ 0.3 мкс/вызов
# первый вызов после importlib.invalidate_caches(): ≈ 2 мкс
    Поиск по кэшированному пути почти бесплатен; дорог find_spec только на холодных путях и родителях-пакетах (16.3 ⚠️).

    B4. Импорт модуля: каталог против zip (60 свежих импортов, медиана):

    Вариант Время
    каталог + готовый .pyc ≈ 58 мкс
    zip + исходник ≈ 396 мкс
    zip + заранее скомпилированный .pyc ≈ 58 мкс

    Zip-импорт не медленнее обычного — если в архиве байт-код. Исходник в zip компилируется на каждый импорт (16.9), и это ×7. Укладывайте в архивы pyc — вопрос лишь соблюдения версий (magic number, 15.2).

    B5. Цена «импортируй сверху»: 

    # импорт urllib.request + xml.etree.ElementTree + argparse + json «сверху»:
# ≈ 15 мс на каждый запуск процесса (то же, что и в B2 минус база)
    Четыре модуля — уже 15 мс; реальные приложения тянут десятки. Перенос импорта из шапки в точку использования — самый дешёвый способ вернуть это время, и -X importtime до и после — доказательство, а не вера.

    Числа ориентировочные: абсолютные значения зависят от машины, ФС и окружения; отношения — стабильны.
