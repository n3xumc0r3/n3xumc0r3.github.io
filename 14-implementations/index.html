    Часть XIV. Не только CPython: кто ещё исполняет Python#

    «Python» в этой книге до сих пор означал CPython — и в 99% случаев это правильное сокращение. Но язык и реализация — разные вещи: спецификация одна, а исполняют её разные программы. Эта часть — про то, что Python можно исполнить не только интерпретатором на C, что это уже много раз делали, и про оболочки (IPython и соседи), которые сами не интерпретаторы, но меняют среду, в которой вы пишете и исполняете код.

    14.1. Язык против реализации: контракт Python#

    Что определяет «язык Python»? Не CPython, а связка: reference — описание языка (Language Reference), документация стандартной библиотеки и тесты CPython, которые де-факто служат исполняемой спецификацией. Всё, что исполняет эту спецификацию, вправе называться реализацией Python — независимо от языка, на котором написано.

    Контракт — это семантика языка, а не внутренности конкретной реализации. За скобками остаются вещи, на которые код опираться не должен, потому что другие реализации их не гарантируют (и CPython не обещает):

    • момент срабатывания деструктора: __del__ при обнулении счётчика ссылок — деталь refcount-модели CPython (8.5), в реализациях с GC-трассировкой объект умрёт позже;
    • значения id() и sys.getrefcount() — детали refcount-модели; на PyPy getrefcount ведёт себя по-другому;
    • интернирование строк (8.1) и кэш малых чисел (8.2) — оптимизации CPython, не языковые гарантии;
    • формат .pyc и magic number (13.2) — внутренний кэш CPython.

    Узнать, кто исполняет код, можно из sys.implementation — у CPython это namespace с name='cpython' и cache_tag='cpython-312' (тем самым тегом из имён pyc-файлов, 13.2).

    Практическое следствие раздельной природы языка и реализации: бинарные C-расширения собираются под конкретный ABI, и тег платформы в имени wheel'а (PEP 425) прямо называет целевую реализацию:

    numpy-2.1.0-cp312-cp312-manylinux_2_17_x86_64.whl   # CPython 3.12
numpy-2.1.0-pp310-pypy310_pp73-manylinux_2_17_x86_64.whl   # PyPy 3.10

    Wheel с тегом cp312 на PyPy не встанет — у PyPy свои сборки (pp…) или установка из исходников. Отсюда правило большого пальца: «чистый Python» на альтернативных реализациях живёт заметно комфортнее, чем код с расширениями — расширения привязаны к ABI CPython.

    14.2. Альтернативные реализации: кто, на чём, зачем#

    Идея «сделать Python не на C» исполнена много раз — от академических проектов до промышленных платформ. Обзор живых и исторических, с причиной существования каждого.

    PyPy — самая известная альтернатива, интерпретатор на RPython (строгое подмножество Python, компилируемое в C) с мета-tracing JIT: JIT не трассирует ваш код напрямую — он трассирует цикл самого интерпретатора и удаляет слои абстракции между уровнями, специализируя исполнение под конкретную программу. На чистом Python-коде (длинные циклы, словари, списки) PyPy в разы быстрее CPython. Слабое место — C-расширения: мост cpyext эмулирует CPython C API, и через границу «C-расширение ↔ JIT-код» выигрыш часто сгорает. Статус: жив и развивается, поддерживает версии CPython с лагом в один-два года — проверяйте актуальный на сайте проекта.

    GraalPy — реализация Oracle Labs поверх Truffle (фреймворк для интерпретаторов с частичной компиляцией из мира JVM). Фишка — на удивление хорошая совместимость с C-расширениями; мотивация — дать Python жить в JVM-экосистеме рядом с Java, JavaScript и другими Truffle-языками.

    MicroPython (и образовательный форк CircuitPython) — Python для микроконтроллеров. Написан на C, но это не CPython: самостоятельная реализация, укладывающаяся примерно в 256 КБ flash и 16 КБ RAM (порядок величин для минимальной конфигурации, не спецификация), с усечённым языком и собственными модулями стандартной библиотеки. Компилирует исходник прямо на устройстве; для горячего кода есть декораторы @micropython.native и @micropython.viper. Живёт на ESP32, Raspberry Pi Pico и сотнях плат, где стандартный CPython не влезает физически:

    # на CPython и MicroPython работает одинаково:
for i in range(5):
    print(i)

# а это — только на MicroPython (модуля machine в CPython нет):
import machine
led = machine.Pin(25, machine.Pin.OUT)   # GPIO на Raspberry Pi Pico
led.toggle()

    Обратная сторона — проверка «влезет ли мой код»: sys.implementation.name на устройстве вернёт 'micropython', и по этому признаку кросс-платформенный код разводит ветки.

    RustPython — реализация на Rust. Зрелость ниже, чем у PyPy, ниша — встраивание и WASM (запуск Python-кода в браузере/среде без установленного интерпретатора). Отдельно стоит Pyodide — это не новая реализация, а полноценный CPython, скомпилированный в WebAssembly, со стандартной библиотекой и numpy в комплекте.

    Историческая линия — пять уроков:

    • Jython (JVM): давал бесшовный мост в Java и настоящие потоки без GIL — но застрял на 2.7 и заморожен. Урок: совместимость с актуальным языком важнее архитектурных красот.
    • IronPython (.NET): та же идея для CLR; после долгой паузы вышла ветка 3.4, живёт в нише.
    • Stackless Python — модификация CPython с микропотоками (tasklets) и стеками вне стека C; годами двигал MMO Eve Online. Нишу съел asyncio (4.13): сопрограммы дешевле tasklets и не требуют отдельного интерпретатора.
    • Pyston: попытка Dropbox ускорить CPython «снаружи» (2014–2017) закрылась; возрождённая как дистрибутив Pyston 2 (2020) на базе CPython 3.8 дала ~20–30% — и снова заснула. Урок: догонять выпуски CPython извне — беговая дорожка; поэтому собственно ускорением с 2021 занимается команда Faster CPython внутри проекта (13.5).
    • CPython без GIL: PEP 703 — не новая реализация, а отдельная сборка того же CPython; в матрицу реализаций её добавлять честно, но полезно помнить, что «CPython» уже не значит ровно одно.

    Сводная таблица:

    Реализация На чём написана Свой байт-код? Статус Зачем существует
    CPython C свой (wordcode) эталон дефолт, reference implementation
    PyPy RPython свой + JIT жив скорость на чистом Python
    GraalPy Java/Truffle свой + JIT жив Python в JVM-экосистеме
    MicroPython C свой, усечённый жив микроконтроллеры, 16 КБ RAM
    RustPython Rust свой развивается WASM, встраивание
    Jython Java байт-код JVM заморожен (2.7) историческая: мост в Java
    IronPython C# байт-код .NET ниша .NET-интеграция
    Stackless C (форк CPython) свой вымирает микропотоки (до asyncio)
    Pyodide C → WASM свой CPython-ский жив Python в браузере

    14.3. Не реализации: Numba, Cython и граница «тот же язык»#

    Рядом с реализациями живут инструменты, которые часто называют ускорителями Python, но интерпретаторами они не являются — и разница принципиальна.

    Numba — JIT-компилятор числового кода: декоратор @njit компилирует функцию в машинный код через LLVM при первом вызове (поэтому первый вызов медленный, а последующие — нативные). Компилируется подмножество языка: числовые скаляры, numpy-массивы, ограниченные конструкции. Numba не исполняет остальной Python — она его не понимает.

    Cython — транспилятор: язык-надмножество Python (с аннотациями типов C) переводится в C-код, который собирается в обычное расширение. Никакой интерпретации — статическая компиляция на этапе сборки.

    Развилка, которая держит голову в порядке: подмножество языка, скомпилированное частично (Numba) против надмножества, скомпилированного заранее (Cython) против того же языка целиком на другом движке (PyPy и все из 14.2). Реализация обязана исполнять язык; ускоритель — нет, и именно поэтому он может быть быстрее на своём участке: меньше динамики, больше гарантий.

    14.4. REPL поверх REPL: IPython, Jupyter и соседи#

    Тот же CPython, другая оболочка — отдельная категория «не-стандартного Python-опыта».

    Стандартный REPL долгое время был аскетичным: readline-подсказки и всё. В 3.13 его заменил _pyrepl — с подсветкой синтаксиса при вводе, честным многострочным редактированием и листанием истории. У нового REPL есть и CLI-ручки: PYTHON_BASIC_REPL=1 возвращает до-3.13 оболочку, PYTHON_HISTORY задаёт файл истории (по умолчанию ~/.python_history), PYTHON_COLORS управляет цветами сообщений (всё — 3.13+), а в 3.14 появились --help-env / --help-xoptions / --help-all — интерпретатор сам рассказывает про свои переменные окружения и -X-опции. Минимальный «свой REPL» — несколько строк stdlib: python -i script.py (после скрипта остаётся интерактивная сессия со всеми его переменными — быстрый способ дебажить), а code.interact() — встроенная интерактивная пауза где угодно в программе, предок всех breakpoint()-практик.

    IPython — то, что многие подразумевают под «питоном в терминале». Это не интерпретатор другой — это другая оболочка над тем же CPython:

    • магии: %timeit (бенчмарк с автоподбором числа прогонов), %run -d, %debug, %prun (профайлер), %autoreload (подхват изменений модулей без перезапуска);
    • интроспекция: obj? — docstring, obj?? — исходник (всё то, что help() и inspect, но на один символ);
    • история выводов: _, __, _8 — результат восьмой ячейки; история сессий — в sqlite в профиле;
    • встраивание: from IPython import embed; embed() превращает любую точку программы в полноценную интерактивную сессию с локальным контекстом — тяжёлая артиллерия вместо print-дебага.

    Как это выглядит вживую (транскрипт типичной сессии):

    In [1]: squares = [x*x for x in range(5)]

In [2]: squares?
Type:        list
String form: [0, 1, 4, 9, 16]
Length:      5
Docstring:   Built-in mutable sequence. …

In [3]: _[2]            # _ — вывод последней ячейки
Out[3]: 4

In [4]: %timeit sum(range(1000))   # магия-бенчмарк: циклы и число прогонов подберутся сами

    Тот же код в стандартном REPL исполняется тем же интерпретатором — разница только в оболочке: автодополнение, магии и история — это слой IPython над CPython, а не другой язык.

    Архитектурная деталь, которая многое объясняет: IPython — библиотека. Терминальный процесс и «ядро» (kernel) — разные сущности: терминальный IPython запускает ядро в себе, а Jupyter — по сети.

    Jupyter — ядро IPython (ipykernel) плюс протокол сообщений поверх ZeroMQ: frontend (ноутбук, консоль, IDE) шлёт ячейки кода, ядро возвращает вывод. Отсюда модель ноутбука: состояние живёт в ядре, а не в файле — и порядок исполнения ячеек не обязан совпадать с порядком в документе. Это главный источник «ноутбук-подводных камней»: код, «работающий» в ноутбуке, может зависеть от переменных, которых в файле нет.

    Соседи по нише: bpython (подсказки сигнатур в реальном времени), ptpython (настраиваемый REPL с vim-режимом), ipdb (pdb с автодополнением IPython).

    Сводка «задача → инструмент»:

    Задача Инструмент
    Пощупать API, прототип, разбор данных ipython
    Отладочная пауза внутри скрипта code.interact(), embed(), breakpoint()
    Отчёт с кодом, выводом и графиками Jupyter
    Ускорить числовое ядро Numba (14.3)
    Ускорить чистый Python целиком PyPy (14.2)
    Код на микроконтроллере MicroPython
    Жить внутри JVM GraalPy / Jython

    Общая мораль части: «Python» — это контракт, и его исполняют многие. CPython остаётся дефолтом не потому, что язык неотделим от него, а потому, что он эталон совместимости, у него самая широкая экосистема C-расширений и с 2021 года его ускорение — приоритет самих разработчиков. Все остальные — осознанный выбор под задачу: скорость (PyPy), размер (MicroPython), платформа (JVM/.NET/WASM), среда (IPython/Jupyter).

    Бенчмарки к Части XIV#

    Замеры на CPython 3.12 (Linux, x86_64); абсолютные числа зависят от машины и диска, отношения — устойчивы.

    1. Старт интерпретатора — цена site и импортов. 

    $ python -c "pass"         # ≈ 0.015 с
$ python -S -c "pass"      # ≈ 0.008 с — без site почти вдвое быстрее
$ python -c "import json"  # ≈ 0.019 с
    Половина старта CPython — это site (11.31): сканирование каталогов, .pth-файлы, импорт sitecustomize. Отсюда ответ на «почему CLI-утилиты на Python медленно стартуют»: сам интерпретатор готов за ~15 мс, остальное — импорты библиотек (уже json добавляет ~5 мс, а тяжёлые пакеты — сотни).

    2. IPython — цена оболочки. 

    $ ipython -c "pass"   # ≈ 1.05 с — ~70× старта python -c pass
    Оболочка (prompt_toolkit, история, магии, ~200 импортированных модулей) дороже самого интерпретатора на два порядка. Для одноразовых скриптов и CI — стандартный REPL или python -c; IPython — интерактивный инструмент, и его стартовая цена того не отменяет (14.4).

    3. Старт: интерпретатор vs реализации. PyPy стартует на порядки дольше CPython (JIT-инфраструктура и импорт большого рантайма), MicroPython на микроконтроллере — на порядки быстрее (нечего импортировать). Замерить в одной таблице честно не выйдет — платформы несравнимы; смотрите бенчмарки самих проектов: speed.pypy.org для PyPy, docs.micropython.org для микро-плат. Урок тот же, что в 14.2: «быстрее» без уточнения нагрузки — не ответ.
